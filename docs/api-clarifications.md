## 2. Перелік уточнених поведінкових аспектів

### 2.1. Пагінація списку референсів (`limit` та `offset`)
- **Початкова вимога SRS:** `REQ-F-005` (кон'юнктивна фільтрація) та `REQ-F-006` (повнотекстовий пошук) вимагають швидкого повернення вибірки без блокування інтерфейсу.
- **Уточнення API:** Для запобігання перевантаженню мережевого каналу та пам'яті клієнта при великій кількості записів у контракт `GET /references` додано обов'язкові параметри постраничного виведення:
  - `limit` (int, default: 50, max: 100) — максимальна кількість референсів в одній відповіді.
  - `offset` (int, default: 0) — зміщення від початку вибірки.
- **Структура відповіді:** Замість плоского масиву введено DTO `ReferenceListResponse`, що містить:
  - `items`: список об'єктів `ReferenceResponseDto`.
  - `total`: загальна кількість знайдених елементів, що задовольняють фільтр.
  - `limit` та `offset`: параметри поточного вікна даних.

### 2.2. Єдина стандартизована модель помилок (RFC 7807 / Problem Details)
- **Початкова вимога SRS:** `REQ-NF-004` (безпека та санітизація) та критерії прийняття передбачають інформування користувача про помилки валідації.
- **Уточнення API:** Для уникнення різнорідних форматів помилок на рівні REST API затверджено єдину схему `ProblemDetails` з `Content-Type: application/problem+json`:
  ```json
  {
    "type": "https://api.design-refs.local/errors/validation-error",
    "title": "Validation Failed",
    "status": 400,
    "code": "VALIDATION_FAILED",
    "detail": "Required fields validation failed.",
    "instance": "/api/v1/references",
    "timestamp": "2026-10-31T14:05:00Z",
    "invalid_params": [
      {
        "name": "title",
        "reason": "Title is required and cannot be empty."
      }
    ]
  }
  ```
  Це дозволяє фронтенд-клієнту однотипно обробляти будь-які помилки (400, 404, 422, 500) без спеціальних парсерів для кожного ендпоінта.

### 2.3. Звіт про міграцію категорій при каскадному перепризначенні
- **Початкова вимога SRS:** `REQ-NF-003` (надійність) вимагає 0% втрати даних при видаленні категорії шляхом автоматичного переводу всіх її референсів у дефолтну категорію `General`.
- **Уточнення API:** Ендпоінт `DELETE /categories/{name}` замість «німого» статусу 204 No Content повертає статус `200 OK` зі структурованим DTO `CategoryMigrationReportDto`:
  ```json
  {
    "message": "Category 'Branding' removed successfully.",
    "reassigned_to": "General",
    "affected_references_count": 4
  }
  ```
  Це надає клієнту негайний аудит-фідбек про те, скільки саме карток було автоматично захищено від знищення.

### 2.4. Системний ендпоінт перевірки працездатності (`GET /health`)
- **Початкова вимога SRS:** `REQ-NF-001` (SLA швидкодії < 50 мс) та `REQ-NF-005` (супровідність).
- **Уточнення API:** Додано операцію `getHealthStatus` (`GET /health`), яка повертає статус готовності сервісу, поточну версію контракту (`1.0.0`) та метрику цільової затримки, що забезпечує автоматизований моніторинг інфраструктури без навантаження на базу даних.
