## Відповіді на контрольні питання

### 1. У чому полягає API-first підхід і чому контракт API створюється до серверної реалізації?
**Відповідь:**
**API-first підхід** — це архітектурна стратегія розробки програмного забезпечення, за якої інтерфейсний контракт прикладного програмування (Application Programming Interface) розглядається як першокласний артефакт системи (first-class citizen) і формалізується як формальна машиннозчитувана специфікація (OpenAPI/Swagger) **до початку написання будь-якого рядка серверного чи клієнтського продуктивного коду**.

**Чому контракт створюється до серверної реалізації:**
1. **Паралелізація інженерних потоків (Decoupled Development):** Наявність затвердженого контракту дозволяє команді розробки клієнтського інтерфейсу (фронтенду) створювати UI-компоненти та логіку стану на основі згенерованого Mock API, не очікуючи готовності бекенду.
2. **Захист від витоку деталей реалізації (Information Hiding):** Коли API проектується «після коду», він зазвичай стає побічним дзеркалом внутрішньої структури реляційної бази даних або мовних класів, що робить клієнт жорстко зв'язаним із бекендом. Створення контракту до кодування фокусується на потребах бізнес-користувача (Consumer-Driven Contract).
3. **Економічна ефективність змін:** Виправлення логічних дефектів, зміна типів полів чи структури маршрутів у текстовому файлі специфікації коштує в десятки разів менше, ніж переписування існуючого коду, міграцій баз даних та зламаних інтеграцій на пізніх фазах SDLC.

### 2. Яку роль OpenAPI specification виконує в SDD-процесі?
**Відповідь:**
У методології **Specification-Driven Development (SDD)** специфікація OpenAPI виконує роль **Центрального єдиного джерела правди (Single Source of Truth) для інтерфейсного рівня системи**, забезпечуючи безперервний міст між абстрактними вимогами бізнесу та програмною реалізацією:
1. **Еталонний контракт для контрольних точок (Stage-Gates):** На фазі `API-GATE` саме відповідність OpenAPI specification критеріям повноти та безпеки визначає дозвіл на перехід до стадії TDD-імплементації (`GO / REVISE`).
2. **Генератор автоматизації:** Специфікація використовується інструментами автоматизованого валідування (`scripts/validate_openapi.py`), генерації контрактних мок-серверів (`scripts/mock_server.py`), клієнтських DTO-типізацій та інтерактивної документації (Swagger UI).
3. **Фундамент для TDD/BDD:** Всі параметри запитів, схеми валідації та структури помилок, зафіксовані в OpenAPI, напряму стають вхідними даними для майбутніх модульних та інтеграційних тестів у ЛР5.

### 3. Як REQ-ID використовуються для перевірки доцільності API operations?
**Відповідь:**
Ідентифікатори вимог (`REQ-F-xxx`, `REQ-NF-xxx`) використовуються як інструмент **двонаправленої простежуваності (Bidirectional Traceability) та аудиту доцільності (Justification Audit)**:
1. **Захист від самовільного функціоналу (Gold Plating Prevention):** Кожна операція в OpenAPI specification обов'язково маркується метаданими `x-req-id` (наприклад, `POST /references` маркується `REQ-F-001` та `REQ-NF-004`). Якщо розробник чи ШІ-агент пропонує операцію, яка не прив'язана до жодного затвердженого `REQ-ID` із базової SRS v1.0, така операція визнається недоцільною та негайно відхиляється.
2. **Контроль повноти покриття вимог (Coverage Verification):** Аудит матриці простежуваності дозволяє гарантувати, що жодна функціональна вимога специфікації не залишилася без відповідного HTTP-методу доступу.
3. **Оцінка ціни відмови:** Операції, пов'язані з вимогами підвищеного ризику (наприклад, безпека `REQ-NF-004` або цілісність даних `REQ-NF-003`), автоматично отримують розширений набір негативних сценаріїв тестування та підвищений рівень аудиту на Gate.

### 4. Чому термінологія API повинна відповідати глосарію предметної області?
**Відповідь:**
Термінологія API повинна суворо відповідати глосарію предметної області для дотримання концепції **Єдиної мови (Ubiquitous Language)**:
1. **Усунення когнітивного розриву (Semantic Alignment):** Коли аналітики, дизайнери, фронтенд- і бекенд-інженери використовують однакові терміни, виключається ризик двозначного тлумачення сутностей. Наприклад, у нашому глосарії чітко розмежовано поняття `Category` (взаємовиключна класифікація 1:1) та `Collection` (тематична користувацька дошка N:M). Якщо в API назвати колекції `boards` чи `folders`, це призведе до плутанини в бізнес-правилах.
2. **Стійкість та ергономіка контракту:** Використання узгоджених назв ресурсів у множині (`/references`, `/collections`, `/categories`) та нормалізованих полів (`tags`, `facet:prefix`, `is_default`) робить API інтуїтивно зрозумілим і передбачуваним для сторонніх інтеграторів.
3. **Відповідність критеріям API-GATE:** Невідповідність назв полів глосарію є прямою підставою для блокування контракту з вердиктом `REVISE`.

### 5. Яка різниця між ресурсом REST API та внутрішнім класом реалізації?
**Відповідь:**
Головна відмінність полягає в **призначенні, рівні абстракції та межах інкапсуляції**:
- **Ресурс REST API** — це зовнішня концептуальна сутність або колекція сутностей, адресовна через стандартизований URI (наприклад, `/api/v1/references/{id}`). Ресурс взаємодіє з зовнішнім світом за допомогою безстатусного протоколу HTTP, передаючи свій стан у вигляді уніфікованих представлень (DTO в JSON-форматі), приховуючи від споживача технологічний стек, структуру бази даних і внутрішні алгоритми.
- **Внутрішній клас реалізації** — це конкретна програмна конструкція мови програмування (наприклад, `class Catalog` чи `class Reference` у Python), яка оптимізована під виконання обчислень, ефективне використання оперативної пам'яті (хеш-таблиці, множини `set()`), управління транзакціями та внутрішню валідацію.
*Приклад:* Внутрішній клас `Catalog` об'єднує в собі всі референси та логіку пошуку, проте в REST API ресурсу `/catalog` взагалі не існує — натомість клієнту надаються гранулярні ресурси `/references` та `/categories`. Це унеможливлює витік деталей внутрішньої реалізації (Information Leakage).

### 6. Для чого необхідна єдина модель помилок API?
**Відповідь:**
Єдина модель помилок (у нашому проєкті — стандарт **RFC 7807 Problem Details**, `application/problem+json`) необхідна для:
1. **Передбачуваної обробки на клієнті:** Фронтенд-застосунок має єдиний уніфікований інтерфейс обробки відповідей з кодами 4xx і 5xx. Розробнику інтерфейсу не потрібно писати окремий парсер під кожен ендпоінт.
2. **Структурованої гранулярності помилок валідації:** Завдяки масиву `invalid_params` клієнт точно знає, яке саме поле форми (`title`, `url` чи `tags`) містить помилку і яке повідомлення слід відобразити під конкретним інпутом.
3. **Безпеки та захисту від витоку даних (OWASP API Security):** Єдина модель гарантує, що у відповідь клієнту ніколи не потраплять внутрішні стек-трейси сервера, імена таблиць БД чи системні шляхи ОС у разі збою (замість цього повертається стандартизований код помилки, наприклад `INTERNAL_ERROR` або `UNSAFE_URL_PROTOCOL`).
4. **Спостережуваності та трасування:** Наявність поля `instance` та часової мітки `timestamp` дозволяє легко пов'язувати помилку користувача з серверними системними логами.

### 7. Чому negative scenarios необхідно проєктувати до реалізації API?
**Відповідь:**
Проєктування негативних сценаріїв (`Negative Scenarios`) до моменту написання коду є критично важливим, оскільки:
1. **Зони найбільшої вразливості та ціни відмови:** Більшість збоїв та інцидентів безпеки стаються не на базовому успішному шляху (Happy Path), а внаслідок граничних або шкідливих запитів (XSS-атаки через `javascript:`, ін'єкції невалідного JSON, спроби видалення захищених системних даних).
2. **Формування точних контрактних меж валідації:** Створення негативних сценаріїв (наприклад, `NEG-01` на відхилення небезпечного протоколу зі статусом 422 або `NEG-04` на заборону видалення базової категорії `General`) чітко визначає HTTP-статуси, коди помилок та правила валідації до того, як розробник почне кодування.
3. **Забезпечення справжнього TDD (Red-Green-Refactor):** У 5-й лабораторній роботі саме ці негативні сценарії будуть перетворені на модульні тести, які спочатку падатимуть (Red), гарантуючи, що код бекенду дійсно надійно захищає систему від аномальних станів.

### 8. Яку функцію виконує mock API до появи серверного коду?
**Відповідь:**
До появи реального серверного коду Mock API виконує наступні ключові функції:
1. **Повне розблокування паралельної розробки (Parallel Engineering):** Клієнтська частина (UI веб-додатка) може розроблятися на повну потужність, звертаючись за реальними HTTP-запитами до запущеного локального мока, отримуючи валідні структури даних і емуляцію затримок мережі.
2. **Перевірка ергономіки та життєздатності контракту (Contract Usability):** Мок дозволяє інженерам «помацати» API на практиці, перевірити зручність query-параметрів фільтрації та пошуку ще до написання коду бізнес-логіки. Якщо виявляється незручність, контракт виправляється за хвилини.
3. **Автоматизована верифікація сценаріїв на API-GATE:** Мок-сервер дозволяє прогнати автоматизований тестовий набір (`scripts/test_mock_scenarios.py`) для позитивних і негативних тестів, доводячи несуперечливість і замкненість спроєктованої моделі.

### 9. Які умови повинні бути виконані для рішення GO на API-GATE?
**Відповідь:**
Для ухвалення позитивного рішення **GO** на контрольній точці API-GATE повинні бути **одночасно і на 100% виконані всі 10 обов'язкових умов**:
1. Кожна суттєва API operation має чіткий і обґрунтований зв’язок із відповідним `REQ-ID`.
2. Назви ресурсів, параметрів та полів суворо відповідають глосарію предметної області.
3. URI та HTTP-методи використовуються послідовно згідно з канонічними принципами REST.
4. Для всіх операцій визначено строгі схеми запитів і відповідей (DTO) без невизначених типів.
5. Визначено вичерпні коди стану HTTP та впроваджено єдину стандартизовану модель помилок.
6. Сформовано повний комплект позитивних і негативних сценаріїв перевірки.
7. Контракт не розкриває деталей внутрішньої програмної реалізації чи будови БД.
8. Специфікація OpenAPI проходить автоматичну валідацію лінтером/валідатором із результатом 0 помилок.
9. Mock API успішно запускається безпосередньо на базі затверджуваної специфікації.
10. Основні позитивні й негативні сценарії успішно відтворюються через Mock API.
*Якщо хоча б одна критична умова порушена — рішення обов'язково має бути `REVISE` з усуненням зауважень.*

### 10. Чому нову поведінку, виявлену під час проєктування API, не можна непомітно додавати до OpenAPI specification?
**Відповідь:**
Непомітне (несанкціоноване) додавання нової поведінки до OpenAPI specification суворо заборонено, оскільки:
1. **Це є грубим порушенням фундаментального принципу SDD:** Затверджена на `SPEC-GATE` специфікація SRS v1.0 є зафіксованою базовою лінією (Baseline). Самовільне внесення змін руйнує дисципліну контролю конфігурації.
2. **Ризик неконтрольованого розростання меж (Scope Creep & Gold Plating):** Додавання неспецифікованих можливостей збільшує обсяг робіт, ускладнює тестування і підвищує ризик виникнення дефектів без оцінки впливу на строки та бюджет проєкту.
3. **Руйнування простежуваності (Broken Traceability):** Нова функція не матиме зв'язку з `REQ-ID`, критеріями прийняття (AC) та сценаріями тестування, створюючи хаос у матриці RTM.
4. **Регламент вирішення:** Якщо під час проєктування API виявлено об'єктивну необхідність у новій поведінці (наприклад, пагінація або спеціалізований звіт про міграцію категорій), вона оформлюється виключно через **офіційне уточнення або Адендум (`docs/api-clarifications.md`)**, що підлягає обов'язковому когнітивному аудиту людиною на етапі Gate.

## Висновки до лабораторної роботи: Які були проблеми при виконанні і як ви їх вирішили
**Відповідь:**
У ході виконання лабораторної роботи №4 було успішно реалізовано повний цикл проєктування REST API за методологією **Specification-Driven Development (SDD)** на основі затвердженої SRS v1.0.

**Виявлені проблеми та способи їх інженерного вирішення:**
1. **Проблема потенційного перевантаження клієнта при великій кількості референсів:**
   *Суть проблеми:* Початкова вимога `REQ-F-005` (фільтрація) описувала отримання списку референсів, але не враховувала обмежень каналу зв'язку при значному зростанні каталогу. Повернення нескінченного плоского списку загрожувало порушенням SLA продуктивності (< 50 мс).  
   *Вирішення:* До специфікації та схеми DTO введено параметри пагінації (`limit`, `offset`) та обгортку `ReferenceListResponse` із загальною кількістю елементів `total`. Зміну офіційно оформлено у вигляді адендуму/уточнення `docs/api-clarifications.md`.
2. **Проблема різнорідності форматів помилок між різними операціями:**
   *Суть проблеми:* Первинні начерки операцій повертали довільні рядкові повідомлення або прості JSON-структури, що ускладнювало розробку клієнтських валідаторів і підвищувало ризик витоку внутрішніх стек-трейсів.  
   *Вирішення:* Архітектурно впроваджено єдину уніфіковану модель помилок за міжнародним стандартом **RFC 7807 (Problem Details)** із типізованими полями `type`, `title`, `status`, `code`, `detail`, `instance` та масивом некоректних параметрів `invalid_params`.
3. **Проблема забезпечення автономності Mock API без залучення важких сторонніх залежностей:**
   *Суть проблеми:* Багато сторонніх мок-інструментів потребують громіздких хмарних платформ або складних конфігурацій, що знижує надійність локального навчального середовища.  
   *Вирішення:* Створено автономний, легковажний Mock API сервер на стандартній бібліотеці Python (`scripts/mock_server.py`), який безпосередньо використовує схеми OpenAPI, реалізує бізнес-правила (кон'юнктивне фільтрування, санітизація XSS, безпечний fallback на `General`) та підтримує швидкісне автоматизоване тестування сценаріїв (`scripts/test_mock_scenarios.py`, 14/14 тестів пройдено з затримкою < 1 мс).
