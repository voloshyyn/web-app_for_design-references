## Чому TDD ефективна та економить час?
TDD дає короткий зворотний зв'язок: дефект виявляється одразу після малої
зміни, а не після інтеграції всієї системи. Тести формалізують критерії
прийняття та автоматично виявляють регресії. Початкове написання тестів
потребує часу; економія виникає завдяки меншій вартості пошуку й виправлення
помилок. Хибний тест не гарантує правильності, тому важливі специфікація,
негативні сценарії та незалежне рев'ю.

## Опишіть цикл TDD
Спочатку читаємо вимогу, AC та контракт. RED: створюємо тест і перевіряємо,
що він не проходить з очікуваної причини. TEST-GATE: звіряємо очікування зі
специфікацією. GREEN: додаємо мінімальний код для потрібної поведінки.
REFACTOR: покращуємо структуру без зміни поведінки, повторюємо тести.
Зберігаємо результати й коміти. Для нової семантики спочатку оформлюємо адендум.

## Як забезпечується покриття коду та тестами?
Матриця простежуваності пов'язує REQ -> AC -> сценарій -> тест -> компонент.
Позитивні, негативні та граничні приклади перевіряють вимоги, а coverage
вимірює виконані рядки коду. У цій роботі є unit/BDD, інтеграційні HTTP та
контрактні перевірки. Покриття рядків не доводить правильність assertions
і не дорівнює повному покриттю вимог. Невиконані людські UX-перевірки
позначені окремо; поріг моделей за SRS становить 95%.

## Чи є новий функціонал рефакторингом?
Ні. Новий функціонал змінює спостережувану поведінку та потребує вимоги,
контракту й нових тестів. Перейменування колекції — розширення ADD-001.
Виділення спільної перевірки назви — рефакторинг зі збереженням поведінки.

## Чим відрізняється рефакторинг від реінжинірингу?
Рефакторинг — локальне покращення внутрішньої структури зі збереженням
зовнішньої поведінки. Реінжиніринг — ширша перебудова наявної системи,
яка може включати аналіз, зміну архітектури, платформи, даних і процесів.
Рефакторинг може бути одним із кроків реінжинірингу.

## Висновки
Реалізовано REST API за затвердженим OpenAPI, локальне збереження,
журналювання дій і автоматичні перевірки. Для ADD-001 виконано послідовність
вимога -> тести RED -> код GREEN -> рефакторинг -> регресія. Перевірено
сумісність базового контракту, цілісність даних та обробку помилок.
Актуальні результати верифікації збережено в logs/lab5-verification.json.
За дорученням користувача валідацію серверних сценаріїв виконав агент;
докази наведено в logs/lab5-agent-validation.json. Це не людський підпис
і не буквальне виконання пункту PDF про валідацію людиною. Історичну
неповноту поетапного RED бази явно зазначено в протоколі. Форму автоматично не надіслано.
