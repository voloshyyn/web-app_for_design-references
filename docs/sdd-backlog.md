## 1. Конфігурація системи багтрекінгу та робочого процесу

### 1.1. Вибір платформи
Для управління задачами обрано **GitHub Issues & Projects**, оскільки проєкт розміщено у відкритому Git-репозиторії `voloshyyn/web-app_for_design-references`. Це забезпечує:
- Пряму інтеграцію комітів (`spec:`, `test:`, `feat:`, `gate:`) із номерами тікетів через семантичні зв'язки (#ID).
- Гнучку систему міток (Labels) для типізації задач за стандартами SDD.
- Прозору історію аудит-логу та відстеження авторства (людина vs ШІ-агент).

### 1.2. Базові статуси задач (Task Lifecycle States)
Життєвий цикл кожної задачі регламентований наступними обов'язковими станами:
1. `1. New / Draft` — задача сформована на основі ідентифікатора вимоги в SRS, очікує перевірки та зв'язування.
2. `2. Backlog / Planned` — задача валідована людиною, визначені залежності, оцінено трудовитрати.
3. `3. In Progress (Dev / TDD)` — активна розробка. Для фіч діє правило блокування: робота починається лише після наявності відповідного тесту.
4. `4. Verification (CI / Testing)` — автоматизований прогін тестів, аналіз покриття коду, бенчмарк швидкодії (SLA < 50 мс), лінтинг PEP 8.
5. `5. Validation (Review / Gate)` — людський когнітивний аудит відповідності задуму, перевірка відсутності gold plating, ухвалення рішень Stage-Gate.
6. `6. Done / Closed` — задача повністю виконана, код злито в `main`, матрицю простежуваності оновлено.
7. `Blocked / Revise` — зупинка виконання через виявлену прогалину або суперечність у SRS (ініціюється процедура Addendum).
8. `Rejected` — задача відхилена людиною через відсутність обґрунтування у специфікації.

## 2. Типи тікетів відповідно до циклу SDD та матриця ролей

| Тип тікета | Префікс | Призначення в SDD-конвеєрі | Основний виконавець | Роль людини (Студента) | Рівень автономності агента |
|---|---|---|---|---|---|
| **Specification** | `SPEC-*` | Опис вимог, бізнес-правил, глосарію та меж системи | Людина (Автор) | Повне авторство та затвердження базової лінії | Асистент (виявлення прогалин у SKED) |
| **Addendum** | `ADD-*` | Формальна версіована зміна SRS після проходження Gate | Людина (Lead) | Авторизація змін, захист від Scope Creep | Заборонено створювати самостійно |
| **Test** | `TEST-*` | Формування BDD/TDD-сценаріїв та acceptance-тестів | ШІ-агент + Людина | Рев'ю тест-кейсів перед кодуванням, верифікація граничних умов | Високий (генерація pytest-коду) |
| **Feature** | `FEAT-*` | Імплементація функціонального коду модуля | ШІ-агент | Контроль стилю, рев'ю Pull Request, верифікація архітектури | Високий (автономна генерація логіки) |
| **Verification** | `VERIF-*` | Автоматизована перевірка тестів, лінтинг, SLA | CI / Авто-раннер | Аналіз звітів проходження тестів | Повний (автоматичний прогін) |
| **Validation** | `VALID-*` | Оцінка юзабіліті, зручності, відповідності концепції | Людина | Головний оцінювач та валідатор бізнес-задуму | Консультант (збір метрик) |
| **Documentation** | `DOC-*` | Оновлення інструкцій, RTM, звітів, user guide | ШІ-агент + Людина | Редагування та фінальне затвердження формулювань | Середній (генерація чернеток) |
| **Gate** | `GATE-*` | Контрольна точка переходу (GO / REVISE / ABORT) | Людина (Lead) | **Виключне право прийняття рішення (Human-in-the-loop)** | **Заборонено ухвалювати рішення** |

> [!IMPORTANT]
> **Принцип суверенітету рішень Gate:** Тікет типу `Gate` не створює виконуваного коду чи тестів. Він виконує функцію шлюзу якості. Рішення на контрольних точках належить виключно людині, що унеможливлює самовільний дрейф поведінки ШІ-агента.

## 4. Порівняння пропозиції агента та коректив студента

У ході виконання роботи ШІ-кодинговий агент запропонував первинний варіант декомпозиції, який було скориговано та покращено студентом:

1. **Усунення передчасного кодування без тестів:**
   - *Пропозиція агента:* Об'єднати написання коду і тестів у спільні задачі `TASK-01` .. `TASK-08`.
   - *Коректива студента:* Суворе розділення на тікети `TEST-*` та `FEAT-*`. Встановлено блокуючу залежність `FEAT-*` від `TEST-*` (реалізація TDD-принципу «спочатку тести, потім код»).
2. **Введення проміжної контрольної точки CORE-GATE:**
   - *Пропозиція агента:* Один фінальний Gate наприкінці всього проєкту.
   - *Коректива студента:* Додано проміжну точку `GATE-CORE` після реалізації ядра та валідації безпеки URL/ін'єкцій. Це зумовлено високою ціною відмови (`REQ-NF-004`, `REQ-NF-003`).
3. **Запобігання кореляції помилок (Prompt Segregation):**
   - *Пропозиція агента:* Повна генерація і тесту, і коду однією підказкою (one-shot).
   - *Коректива студента:* Запроваджено обов'язковий етап ручного рев'ю тест-кейсів людиною (`TEST-01` виконується у ролі `Joint`), щоб агент не створював тавтологічних хибно-позитивних тестів.
4. **Виправлення оцінки трудовитрат (Human Bottleneck):**
   - *Пропозиція агента:* Рівномірний час виконання для всіх задач (~30 хв на кожну).
   - *Коректива студента:* Збільшено оцінку часу людини на етапах валідації та Stage-Gates, оскільки когнітивне навантаження людини є головним фактором тривалості критичного шляху.
