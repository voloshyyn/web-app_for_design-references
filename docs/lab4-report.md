## 2. Модель REST-ресурсів та декомпозиція предметної області

Відповідно до глосарію та вимог SRS, предметну область системи каталогізації дизайн-референсів декомпозовано на такі фундаментальні ресурси:

```
/api/v1
  ├── /references                        # Колекція референсів (створення, фільтрація, пошук)
  │     └── /{id}                        # Одиничний референс (перегляд картки, редагування, видалення)
  │
  ├── /collections                       # Користувацькі колекції / проєктні дошки
  │     └── /{id}                        # Деталі колекції з переліком прив'язаних референсів
  │           └── /references/{ref_id}   # N:M зв'язок (асоціація / дисоціація референсу з дошкою)
  │
  ├── /categories                        # Довідник категорій верхнього рівня
  │     └── /{name}                      # Одинична категорія (безпечне видалення з Fallback to 'General')
  │
  └── /health                            # Інфраструктурний ресурс перевірки статусу та SLA
```

### Принципи проєктування інтерфейсу:
1. **Іменники у множині:** Усі ресурси верхнього рівня позначаються іменниками у множині (`references`, `collections`, `categories`).
2. **Канонічні HTTP-дієслова:** 
   - `GET` — безпечне, ідемпотентне читання ресурсів чи вибірок;
   - `POST` — створення нового екземпляра сутності або створення асоціації;
   - `PUT` — ідемпотентна заміна/оновлення атрибутів ресурсу;
   - `DELETE` — ідемпотентне безпечне видалення.
3. **Ізоляція внутрішнього стану:** Внутрішній клас-агрегат `Catalog` приховано. Зовнішній споживач API взаємодіє виключно з адресовними ресурсами, не маючи доступу до внутрішніх структур пам'яті чи ORM.

## 4. Схеми даних запитів і відповідей (DTO)

Усі структури даних у специфікації `spec/openapi.yaml` формалізовано через незалежні схеми (Data Transfer Objects):

1. **`ReferenceResponseDto`:** Повне представлення референсу (`id`, `title`, `url`, `image_url`, `category`, `tags`, `notes`, `created_at`).
2. **`ReferenceCreateDto`:** Вхідний DTO створення (`title` обов'язковий minLength: 1, `url` з регулярним виразом `^https?://`, опціональні `image_url`, `category`, `tags`, `notes`).
3. **`ReferenceUpdateDto`:** DTO часткової або повної модифікації полів.
4. **`ReferenceListResponse`:** Обгортка списку з атрибутами пагінації (`items`, `total`, `limit`, `offset`).
5. **`CollectionResponseDto` / `CollectionWithReferencesDto`:** Представлення колекцій із лічильником елементів та переліком ID.
6. **`CategoryResponseDto` / `CategoryCreateDto`:** Моделі категорій з ознакою захищеності `is_default`.
7. **`CategoryMigrationReportDto`:** Спеціалізоване DTO звіту про автоматичне перепризначення референсів.

## 5. Єдина модель помилок (RFC 7807 Problem Details)

Для всіх виняткових та помилкових ситуацій стандартизовано єдиний тип відповіді `application/problem+json` за стандартом **RFC 7807 / RFC 9457**:

```json
{
  "type": "https://api.design-refs.local/errors/validation-error",
  "title": "Validation Failed",
  "status": 400,
  "code": "VALIDATION_FAILED",
  "detail": "Required fields validation failed.",
  "instance": "/api/v1/references",
  "timestamp": "2026-10-31T14:05:00Z",
  "invalid_params": [
    {
      "name": "title",
      "reason": "Title is required and cannot be empty."
    }
  ]
}
```

### Застосовані машиннозчитувані коди помилок (`code`):
- `UNSAFE_URL_PROTOCOL` (HTTP 422) — порушення вимоги безпеки `REQ-NF-004` (спроба ін'єкції `javascript:`, `data:`).
- `VALIDATION_FAILED` (HTTP 400) — відсутність обов'язкових полів або некоректна довжина.
- `RESOURCE_NOT_FOUND` (HTTP 404) — запит неіснуючого референсу чи колекції.
- `PROTECTED_RESOURCE` (HTTP 400) — спроба видалення системної категорії `General` (`REQ-NF-003`).
- `MALFORMED_JSON` (HTTP 400) — синтаксична помилка парсингу тіла запиту.
- `INTERNAL_ERROR` (HTTP 500) — непередбачена внутрішня аварія сервера.
