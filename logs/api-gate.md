## 1. Мета та призначення контрольної точки

Контрольна точка **API-GATE** є обов'язковим шлюзом якості в методології **Specification-Driven Development (SDD)**. Вона виконується після завершення декомпозиції предметної області на REST-ресурси, розробки OpenAPI specification (v3.0.3), її автоматичної валідації та перевірки на мок-сервері, але **строго ДО початку написання серверної реалізації та коду бізнес-логіки (ЛР5)**.

Мета — зафіксувати стабільний, формально валідований інтерфейсний контракт між клієнтом і сервером, запобігти витоку деталей внутрішньої реалізації, унеможливити неузгоджені зміни вимог (Gold Plating) та гарантувати готовність до паралельної розробки за TDD.

## 2. Чек-лист перевірки критеріїв API-GATE

| № | Критерій оцінки якості контракту | Фактичний стан у проєкті | Результат |
|---|---|---|:---:|
| **1** | Кожна суттєва API operation має обґрунтований зв’язок з `REQ-ID`. | Усі 15 операцій API містять явні анотації `x-req-id` (`REQ-F-001`..`008`, `REQ-NF-001`..`005`). Зв'язок зафіксовано в RTM. | **PASSED** |
| **2** | Ресурси та термінологія відповідають предметній області та глосарію. | Імена ресурсів (`references`, `collections`, `categories`), фасети (`style:value`) та поля DTO строго узгоджені з `spec/glossary.md`. | **PASSED** |
| **3** | URI та HTTP-методи використовуються послідовно. | Дотримано конвенцій REST: іменники у множині, стандартні дієслова HTTP (GET для читання, POST для створення, PUT для заміни, DELETE для видалення). | **PASSED** |
| **4** | Для операцій визначені request і response schemas. | Описано 13 компонентних схем у `components/schemas` з типами, обмеженнями довжини, регулярними виразами та детальними прикладами. | **PASSED** |
| **5** | Визначені необхідні коди стану HTTP та єдина модель помилок. | Визначено коди 200, 201, 204, 400, 404, 422, 500. Усі помилки використовують стандартизовану модель `ProblemDetails` (RFC 7807). | **PASSED** |
| **6** | Передбачені позитивні й негативні сценарії. | Сформовано 8 позитивних сценаріїв (`POS-01`..`POS-08`) та 6 негативних сценаріїв (`NEG-01`..`NEG-06`), що покривають граничні випадки та безпеку. | **PASSED** |
| **7** | API не розкриває без необхідності деталі внутрішньої реалізації. | Контракт використовує спеціалізовані DTO. Внутрішні структури БД, стек-трейси, ORM-моделі та системні шляхи приховані від зовнішнього споживача. | **PASSED** |
| **8** | OpenAPI specification проходить автоматичну валідацію. | Скрипт `scripts/validate_openapi.py` перевірив специфікацію `spec/openapi.yaml`. Виявлено: 0 синтаксичних помилок, 0 порушених посилань `$ref`, 0 попереджень. | **PASSED** |
| **9** | Mock API запускається на основі затверджуваної специфікації. | Мок-сервер `scripts/mock_server.py` запущено автономно на порту 8000 без написання продуктового сервера. | **PASSED** |
| **10** | Основні позитивні й негативні сценарії відтворюються через mock API. | Скрипт `scripts/test_mock_scenarios.py` виконав 14 з 14 сценаріїв зі 100% успіхом та середньою затримкою 0.7 мс (звіт `logs/mock-validation-report.md`). | **PASSED** |
