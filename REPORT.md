## 1. Мета роботи
Опанувати організацію репозиторію інформаційної системи як єдиного сховища артефактів SDD-циклу (Specification-Driven Development). Набути практичних навичок використання Git для версіювання специфікацій, програмного коду, тестів, документації та журналів взаємодії з кодинговим агентом. Засвоїти принципи розмежування змін, створених людиною та агентом, і порядок вирішення конфліктів із використанням специфікації як еталона (контрольна точка GIT-GATE).

## 4. Модель гілкування та конвенція комітів

### 4.1. Конвенція комітів SDD
Для простежуваності артефактів застосовано семантичні префікси:
- `spec:` — правки концептуальних документів та специфікацій вимог (`/spec`).
- `feat:` — зміни у програмному коді системи (`/src`).
- `test:` — додавання або модифікація тестів (`/tests`).
- `docs:` — оновлення регламентів та документації (`/docs`).
- `gate:` — фіксація вердиктів контрольних точок якості та злиття (`/logs`).

### 4.2. Модель гілкування
- `main` — стабільна основа репозиторію.
- `agent/feature-tagging` — гілка, згенерована ШІ-агентом для реалізації швидкого пошуку.
- `human/feature-tagging` — гілка з ручною зміною для введення ієрархічної таксономії.

## 5. Перелік використаних команд Git

| Команда | Призначення |
| :--- | :--- |
| `git init -b main` | Ініціалізація локального сховища з головною гілкою `main` |
| `git config user.name / user.email` | Встановлення ідентифікаційних даних автора комітів |
| `git add <шлях>` | Додавання змінених артефактів до області індексу (staging area) |
| `git commit -m "<повідомлення>"` | Фіксація змін із дотриманням SDD-префіксів |
| `git checkout -b <назва_гілки>` | Створення нової ізольованої гілки та перехід до неї |
| `git checkout main` | Повернення до головної гілки |
| `git merge agent/feature-tagging --no-ff` | Злиття гілки агента зі збереженням топології дерева |
| `git merge human/feature-tagging` | Злиття гілки з ручними змінами (виклик конфлікту) |
| `git status` | Інспекція статусу робочої копії та стану розв'язання конфлікту |
| `git diff` | Порівняння змін між гілками та виявлення конфліктних маркерів |
| `git log --graph --all --oneline` | Візуалізація графа історії комітів та злиттів |

## 6. Моделювання та розв'язання конфлікту (GIT-GATE)

### 6.1. Зміст змін сторін
У файлі `src/models.py` одночасно модифіковано структуру збереження атрибута `tags`:
- **Зміна Агента (`agent/feature-tagging`):** Використано пласку множину рядків `Set[str]` та метод `matches_tag` з часовою складністю $O(1)$ для миттєвої фільтрації референсів.
- **Зміна Людини (`human/feature-tagging`):** Використано багаторівневий словник `Dict[str, str]` для побудови глибинного дерева категорій (таксономії).

### 6.2. Фіксація конфлікту Git
Під час виконання `git merge human/feature-tagging` зафіксовано:
```text
Auto-merging src/models.py
CONFLICT (content): Merge conflict in src/models.py
Automatic merge failed; fix conflicts and then commit the result.
```

### 6.3. Обґрунтування розв'язання за еталоном специфікації
Згідно з принципами SDD, конфлікт вирішено **не за часовою ознакою і не за фактором авторства (людина проти ШІ)**, а за відповідністю первинному задуму системи у `spec/concept.md`:
1. Головна мета системи: *«швидкий пошук дизайн-референсів під час роботи над проєктами»*.
2. Вимога FR-4: *«миттєва фільтрація за комбінацією тегів без перевантаження сторінки»*.
3. Варіант агента (`Set[str]`) точно реалізує швидку перехресну фільтрацію без перевантаження дизайнера введенням складних просторів імен під час збереження знахідок.
4. **Рішення GIT-GATE:** Прийнято структуру пласких тегів агента. Потребу складної таксономії винесено у файл відкритих питань `logs/lab2-open-questions.md` для дослідження під час розроблення повної специфікації вимог (SRS) у Лабораторній роботі №2.
5. Злиття закрито комітом: `gate: resolve tagging conflict prioritized by fast-search spec intent`.
