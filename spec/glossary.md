# Глосарій предметної області (Domain Glossary / Ubiquitous Language)

Цей документ фіксує єдину термінологію проєкту **«Система каталогізації та швидкого пошуку дизайн-референсів»** (`web-app_for_design-references`). 
Всі терміни є обов'язковими для використання в специфікаціях, назвах задач (ішью), коді програмних модулів, ідентифікаторах тестів та користувацькій документації.

---

## 1. Базові сутності системи

| Термін (Укр) | Термін у коді (En) | Означення та семантика |
|---|---|---|
| **Референс** | `Reference` | Основна одиниця даних у системі. Представляє збережений зразок дизайну (веб-сайт, мокап, ілюстрацію, UI-патерн), що містить обов'язкові атрибути (унікальний ідентифікатор, заголовок, URL-джерело, категорію, дату додавання) та необов'язкові (посилання на зображення-прев'ю, персональні нотатки, множину тегів). |
| **Категорія** | `Category` | Взаємовиключна класифікаційна група верхнього рівня, що визначає домен або вид візуального мистецтва (наприклад: *UI/UX*, *Typography*, *Branding*, *3D*, *Motion*, *Illustration*). Кожен референс строго належить рівно до однієї категорії (1:1). За замовчуванням призначається системна категорія `General`. |
| **Колекція** | `Collection` | Тематична дошка (board) або проєктна папка, створювана користувачем для групування референсів під конкретні завдання чи клієнтські проєкти. Відношення з референсами: багато-до-багатьох (N:M). Референс може не належати до жодної колекції або належати до кількох одночасно. |
| **Тег** | `Tag` | Текстова мітка-дескриптор, призначена для швидкого маркування візуальних характеристик, елементів інтерфейсу чи настрою (наприклад: `#minimalism`, `#dark-mode`, `#onboarding`). Зберігається у вигляді нормалізованого рядка в нижньому регістрі без пробілів. |
| **Фасетний тег** | `Facet Tag` | Спеціалізований різновид тегу з префіксом простору назв у форматі `namespace:value` (наприклад: `style:brutalism`, `color:monochrome`, `device:mobile`). Дозволяє здійснювати параметризовану фільтрацію без необхідності створення окремих жорстких таблиць у схемі даних. |
| **Нотатка** | `Note` | Довільний текстовий коментар користувача, прив'язаний до конкретного референсу, що містить аналітичні зауваження, інсайти або ідеї щодо використання дизайн-елемента. |

## 2. Операційні поняття та процеси

| Термін (Укр) | Термін у коді (En) | Означення та семантика |
|---|---|---|
| **Кон'юнктивна фільтрація** | `Conjunctive Filtering (AND)` | Режим пошуку, за якого у вибірку потрапляють лише ті референси, які містять **усі** вибрані користувачем теги (перетин множин). Забезпечує точне звуження каталогу під час роботи над специфічною концепцією. |
| **Повнотекстовий пошук** | `Full-Text Search` | Алгоритм підбору референсів за входженням підрядка запиту в поля `title`, `notes` або строкові представлення тегів без урахування регістру символів. |
| **Простір пошуку** | `Search Space` | Актуальна множина всіх валідних референсів користувача, яка завантажена в робочу пам'ять або локальне сховище для миттєвої обробки запитів. |
| **Санітизація URL** | `URL Sanitization` | Процедура валідації та очищення введених посилань для запобігання атакам типу Stored XSS або ін'єкцій небезпечних протоколів (`javascript:`, `data:`). Допускаються виключно схеми `http://` та `https://`. |
| **Каскадне перепризначення** | `Fallback Reassignment` | Механізм захисту цілісності даних: у разі видалення користувацької категорії всі асоційовані з нею референси не знищуються, а автоматично переводяться у дефолтну категорію `General`. |

## 3. Методологічні поняття розробки (SDD)

| Термін | Означення |
|---|---|
| **SDD (Specification-Driven Development)** | Методологія розробки ПЗ, за якої формальна, верифікована людьми специфікація вимог виступає єдиним джерелом правди (Single Source of Truth) та еталоном для автоматизованої генерації коду, тестів і документації кодинговим агентом. |
| **SKED (Structured Knowledge Elicitation Dialogue)** | Структурований діалог між інженером (експертом предметної області) та мовною моделлю, спрямований на виявлення прихованих припущень, усунення двозначностей та фіксацію консенсусного простору знань до початку написання коду. |
| **SPEC-GATE** | Обов'язкова контрольна точка контролю якості, на якій людина-інженер проводить ретельну інспекцію створеної специфікації, перевіряє її за критеріями якості (повнота, несуперечність, тестованість) та затверджує як базову лінію. |
| **Адендум (Addendum)** | Формальний версіований документ-додаток до специфікації, який створюється після затвердження базової лінії SPEC-GATE у разі потреби додати нові функції чи змінити існуючі вимоги на наступних ітераціях SDLC. |
| **Критерій прийняття (Acceptance Criteria, AC)** | Чітко сформульована, спостережувана умова або набір умов, виконання яких однозначно свідчить про те, що вимога реалізована коректно та готова до приймання. |
| **BDD-сценарій (Given-When-Then)** | Поведінковий тест-кейс, записаний зрозумілою людині та машинам мовою, що описує передумови (Given), подію/дію користувача (When) та очікуваний результат (Then). |
| **Матриця простежуваності (Traceability Matrix)** | Двовимірна таблиця, що забезпечує наскрізний зв'язок між вимогами бізнесу, критеріями прийняття, тестами, кодом програмних компонентів та документацією. |
